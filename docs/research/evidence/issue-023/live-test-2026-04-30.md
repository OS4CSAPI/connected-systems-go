## Test — undeclared fields silently accepted and round-tripped

Setup: DS schema declares only two Quantity fields: `baro_altitude`
(optional) and `geo_altitude` (required).

```
POST /datastreams/c838cd58.../observations
{
  "phenomenonTime": "2026-04-30T11:00:00Z",
  "resultTime":     "2026-04-30T11:00:00Z",
  "result": {
    "geo_altitude": 10500,
    "undeclared_extra_field": "surprise",
    "another_typo_field": 42
  }
}
→ 201
Location: /observations/d21a2f6a-699d-4e19-8b6c-f47ff157e742
```

Round-trip GET:

```
GET /observations/d21a2f6a-699d-4e19-8b6c-f47ff157e742
result:
  geo_altitude:           10500
  another_typo_field:     42
  undeclared_extra_field: "surprise"
```

Confirmed: undeclared keys are silently accepted by the validator and
persisted verbatim. This matches the body's claim and is an
intentional or unintentional **open-schema** policy that is not
documented in the repo.

## Implication

A client typo such as `geo_atltidue` instead of `geo_altitude` will:

1. Cause `geo_altitude` to be treated as absent → 400 *if* the original
   was required.
2. Silently persist `geo_atltidue` as if it were a deliberate
   extension.

For optional fields, a typo would silently succeed with no value
written for the intended field — a real data-quality risk.

## Recommendation (informs the deliverable)

The doc page #23 proposes should explicitly state which of the
following is the project's policy:

- **Strict** (recommended for safety): reject undeclared fields with a
  structured error indicating which fields were unknown.
- **Open with warning** (compromise): accept and persist, but include
  a `Warning` HTTP header listing unknown field names so clients can
  detect typos at integration test time.
- **Silent open** (current): accept, persist, no signal.

Current behaviour is "silent open"; the doc should at least *name*
this policy if it is to be retained, so users can rely on it.
