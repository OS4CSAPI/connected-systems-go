# Issue #11 — Live test (2026-04-30)

Endpoint: `https://129-80-248-53.sslip.io/csapi-go-head`
Server `Date:` header at probe: `Thu, 30 Apr 2026 22:47:41 GMT`.
Datastream: `cf4cd80c-ddc1-4470-815c-292a68463f3e` (DS without uid A, output=temperature).

## Setup

Three observations seeded via `POST /datastreams/{id}/observations`, all returning HTTP 201:

| obs | resultTime               | phenomenonTime           | result |
|-----|--------------------------|--------------------------|--------|
| 1   | `2024-01-15T12:00:00Z`   | `2024-01-15T12:00:00Z`   | 21.5   |
| 2   | `2025-06-15T12:00:00Z`   | `2025-06-15T12:00:00Z`   | 22.5   |
| 3   | `2026-04-29T12:00:00Z`   | `2026-04-29T12:00:00Z`   | 23.5   |

Baseline `GET /datastreams/{id}/observations?limit=10` → HTTP 200, returns all 3 observations sorted `result_time DESC`.

## Tests

All requests `GET /datastreams/{id}/observations?<qs>`. Each row records HTTP status, count of items returned, and which observations were included.

| # | Query string                                                            | Expected (per spec)                | Observed (HTTP / count / items)              | Pass? |
|---|-------------------------------------------------------------------------|------------------------------------|----------------------------------------------|-------|
| 1 | `resultTime=latest`                                                      | only obs 3 (most recent)           | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 2 | `resultTime=latest&limit=1`                                              | only obs 3                          | 200 / 1 / obs3 (correct **by accident** — `ORDER BY result_time DESC LIMIT 1`) | FAIL\* |
| 3 | `resultTime=2099-01-01T00:00:00Z/2099-12-31T23:59:59Z`                   | empty (no observations in 2099)    | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 4 | `resultTime=frobnicate`                                                  | HTTP 400 (invalid)                  | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 5 | `resultTime=2024-01-01T00:00:00Z/2024-01-31T23:59:59Z`                   | only obs 1                          | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 6 | `phenomenonTime=now`                                                     | empty or only "current" obs         | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 7 | `phenomenonTime=2025-01-01T00:00:00Z/2025-12-31T23:59:59Z`               | only obs 2                          | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 8 | `resultTime=../2024-12-31T23:59:59Z` (open-start)                        | only obs 1                          | 200 / 3 / obs1+obs2+obs3                     | FAIL  |
| 9 | `resultTime=2025-01-01T00:00:00Z/..` (open-end)                          | obs 2 + obs 3                       | 200 / 3 / obs1+obs2+obs3                     | FAIL  |

\* T2 returns 1 item but only because `LIMIT 1` is applied to an unfiltered, `result_time DESC`-sorted page. The issue reporter notes this same accidental coincidence.

## Conclusion

Every probe returns the unfiltered default page, including:
- Spec keyword `latest` (T1, T2)
- A fully-future window with zero possible matches (T3)
- Pure garbage that ought to fail validation (T4)
- A narrow valid window that matches exactly one observation (T5, T7)
- Both half-open interval forms (T8, T9)

Status code is uniformly 200; no temporal `WHERE` clause is reaching the SQL. The behaviour is exactly what the static analysis predicts: `ParseTimeRange([]string)` → `ToTimeRangeFromSlice` produces `TimeRange{nil, nil}`, and `applyFilters` adds no `WHERE` clause when both bounds are nil.

After tests, all three seeded observations were deleted via `DELETE /observations/{id}` (HTTP 204).
