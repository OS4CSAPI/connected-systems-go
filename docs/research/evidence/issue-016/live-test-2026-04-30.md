## Setup

```powershell
$BASE='https://129-80-248-53.sslip.io/csapi-go-head'
# Create system
POST /systems  →  201 Created  Location: /systems/a99d5adc-565e-434b-8e0c-17561d1337af
$sysId = 'a99d5adc-565e-434b-8e0c-17561d1337af'

# Create datastream under system
POST /systems/$sysId/datastreams  →  201 Created
  Location: /datastreams/2c28b903-ab1d-45a9-9dd1-9718b0ddf30d
$dsId = '2c28b903-ab1d-45a9-9dd1-9718b0ddf30d'
```

The `POST /systems/{id}/datastreams` flow inserts a `system_datastreams` join
row in `ControlStreamRepository.Create` analogue (datastream side, in
`populateSystemAssociations`), so `$dsId` has both sides of the m2m.

## T1 — Non-cascade datastream DELETE

```
DELETE /datastreams/2c28b903-ab1d-45a9-9dd1-9718b0ddf30d
HTTP/1.1 500 Internal Server Error
{"error":"Failed to delete datastream"}
```

Even **non-cascade** trips the FK `fk_system_datastreams_datastream`. This
demonstrates that the cascade flag is not the issue — the join cleanup is
missing on every code path.

## T2 — `?cascade=true` datastream DELETE (issue's primary symptom)

```
DELETE /datastreams/2c28b903-ab1d-45a9-9dd1-9718b0ddf30d?cascade=true
HTTP/1.1 500 Internal Server Error
{"error":"Failed to delete datastream"}
```

**Bug 1 reproduced verbatim.** Issue body's T8 result reproduces 1:1.

## T3 — `?cascade=true` system DELETE

```
DELETE /systems/a99d5adc-565e-434b-8e0c-17561d1337af?cascade=true
HTTP/1.1 500 Internal Server Error
{"error":"Failed to delete system"}
```

**Bug 1 reproduced for system path.** Issue body's T11 result reproduces 1:1.

## T4 / T5 — Resources still exist after 500

```
GET /datastreams/2c28b903-...   HTTP/1.1 200 OK
GET /systems/a99d5adc-...       HTTP/1.1 200 OK
```

The transaction was rolled back; both resources still exist. This is the
correct behaviour for a failed transactional cascade — but it leaves the
client with no path to actually delete them.
