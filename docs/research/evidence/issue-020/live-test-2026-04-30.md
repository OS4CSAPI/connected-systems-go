## Test matrix — `resultTime` error message

`Content-Type: application/json` and the body shown.

## Findings

- T1 (issue body's case) reproduces verbatim: numeric `1773100000.0` →
  `"resultTime is required"` even though the field IS present in the body.
- T2 confirms the only path with a distinct, accurate message: malformed
  RFC 3339 string `"2026-04-30"` (date-only, no time-of-day) → `"Invalid resultTime format"`.
- T3 is the genuinely-missing baseline.
- T4-T7 confirm the message-conflation: every wrong-type variant (null,
  empty string, number, object, bool) all collapse to the same misleading
  `"resultTime is required"` message.

## Distinguishability

The current implementation produces exactly **2 distinct error messages**
across the 7 distinct client error classes shown above:

- 1 client error → distinct accurate message (T2).
- 6 client errors → conflated misleading message (T1, T3, T4, T5, T6, T7).

A client receiving `"resultTime is required"` cannot distinguish:

- "I forgot to include the field" (T3)
- "I sent JSON null" (T4)
- "I sent an empty string" (T5)
- "I sent a numeric epoch by mistake" (T1)
- "I sent the field as an object/bool by mistake" (T6, T7)

…from each other. This is the developer-time-waste UX defect the issue
body identifies.

## Spec / authority context

The CSAPI Part-1 schema declares `resultTime` as a string (date-time format).
RFC 7159 / RFC 8259 §3 distinguishes `null` from missing (`null` is a
defined value of type "null", not equivalent to absence). RFC 7807 (Problem
Details for HTTP APIs) recommends that error responses identify the
specific cause to enable client-side remediation. The current single
message defeats that purpose for 6 of the 7 cases.
