## 2. `GET /controlstreams?limit=1` — empty collection (latent leak)

```pwsh
$ curl.exe -s "$base/controlstreams?limit=1"
{"items":[],"links":[{"href":".../controlstreams?limit=1","rel":"self"}]}
```

There are no controlstreams on HEAD to test, but `control_stream.go:53`
has the **identical** untagged `Systems []System` field, and the
controlstream handler uses the same direct-`json.Marshal` path as
the datastream handler. The leak will reproduce as soon as a
controlstream exists. This is documented as an adjacent finding in
the static analysis (out of scope for issue #15 by the issue's own
"file separately" rule).

## 3. `GET /systems/{id}` — no leak (manual DTO)

```pwsh
$ curl.exe -s "$base/systems/666ed3fe-bccf-4670-bb85-a0a3c4562772"
{
  "type": "Feature",
  "id": "666ed3fe-bccf-4670-bb85-a0a3c4562772",
  "geometry": null,
  "properties": { "uid": "…", "name": "…", "featureType": "…" },
  "links": [ … ]
}
```

No `Procedures`/`Deployments`/`Datastreams`/`Controlstreams`/
`SamplingFeatures` keys in this response, even though the corresponding
struct fields in `system.go:65–70` are also untagged. This confirms
the static-analysis finding: the System handler builds a custom GeoJSON
`Feature` DTO rather than marshalling the GORM struct directly, so
those fields are latent rather than visible.
