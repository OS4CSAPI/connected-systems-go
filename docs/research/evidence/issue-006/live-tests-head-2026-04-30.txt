Findings T1:
  (a) `system@link` is emitted as a JSON object with a single `href` property — spec
      compliant (only `href` is required), but minimal: no rel/type/title/uid.
  (b) `system@link.href` is RELATIVE: "systems/<uuid>". Spec declares
      `format: uri` (typically absolute) with absolute example.
  (c) `system@id` is NOT emitted (matches spec — that field is not defined on
      Datastream).
  (d) `links[]` array DOES include an absolute URL pointing at the parent system
      with `rel: "ogc-rel:systems"` — a second discoverability path for clients.
  (e) Capital-S `Systems":null` leak is still present (not the focus here, tracked
      separately).

Summary
-------
cs-go HEAD emits cross-resource references EXACTLY per OGC 23-002:
  - Datastream/ControlStream parent: `system@link` (object)  ✅
  - Observation/Command parent:      `datastream@id` / `controlstream@id` (string) ✅
  - In-collection sibling refs:      `samplingFeature@id` (string) on obs/cmd  ✅
  - Cross-collection refs:           `procedure@link` (object) on obs/cmd  ✅

Two minor conformance/UX gaps observed:
  G1: `system@link.href` is a relative path; spec example is absolute URI.
  G2: `system@link` carries only `href` (no rel/type/title/uid) — minimal but
      still spec-compliant. Adding type/title would help client UX without
      changing conformance.

The premise of issue #6 (and the SensorHub interop comparison) is INVERTED:
SensorHub's `system@id`-on-datastream is the non-conformant shape; cs-go's
`system@link`-on-datastream is the conformant shape. The correct fix for
client interop is on the CLIENT side (already done in ogc-client-CSAPI_2 #166)
or on SensorHub. cs-go should NOT add `system@id` on Datastream/ControlStream.
