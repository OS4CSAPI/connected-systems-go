5. Why the issue's framing is wrong
   ---------------------------------
   - The issue cites "OGC 23-001 §7.3 — Query parameters: Spec defines
     `uid` as a standard list filter parameter". Direct inspection of
     opengeospatial/ogcapi-connected-systems part1 OAS (canonical source)
     shows the parameter name is `id`, not `uid`, and the parameter
     description explicitly enumerates "Local IDs or Unique IDs (URI)".
   - Adding a separate `UIDs` field plus per-repo `unique_identifier IN ?`
     branch (Option A in the issue) would create a redundant code path
     for a parameter that is already covered by the spec parameter.
   - Adding `uid` as an alias that maps into `IDs` (Option B in the issue)
     is functionally a no-op — `?id=urn:...` already works the same way.
     It is purely a SensorHub-compat convenience alias.

6. SensorHub interop note (the actual root cause of the symptom)
   --------------------------------------------------------------
   OSH SensorHub apparently DOES accept `?uid=`. That is a SensorHub
   non-spec extension (or, more charitably, a pre-23-001 idiom from the
   SOS 2.0 era). The OSHConnect-Python publisher inherited this idiom and
   sent `?uid=urn:...` to cs-go, where the parameter is silently ignored
   (Go's `url.Values.Get` returns "" for unknown keys, same as for any
   typo such as `?foo=bar`), so the publisher saw the full collection.
   The publisher's correct fix is `?id=urn:...`, which is one character
   shorter, spec-compliant, and works on cs-go today (verified live in
   live-tests-head-2026-04-30.txt).

7. The narrower defect that is actually present
   ---------------------------------------------
   Unknown query parameters are silently ignored across the API surface
   (verified by `?foo=bar` test). For `?uid=` specifically this is a
   publisher-side discoverability footgun. The same hazard exists for any
   misspelling of any documented parameter (`?lmiit=10`, `?systemId=x`).
   This is candidate for a docs/UX follow-up, not a bug — OGC API Common
   does not mandate strict-unknown-param rejection.
