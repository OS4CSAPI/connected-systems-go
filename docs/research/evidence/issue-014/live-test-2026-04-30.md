## 1. `GET /api` returns the 88-byte stub

```text
$ curl -s -i $base/api
HTTP/2 200
content-type: application/vnd.oai.openapi+json;version=3.0
content-length: 88
date: Thu, 30 Apr 2026 ...

{"openapi": "3.0.0", "info": {"title": "OGC Connected Systems API", "version": "1.0.0"}}
```

- **Status:** 200
- **Content-Type:** `application/vnd.oai.openapi+json;version=3.0` (OAS
  3.0 JSON media type per OGC 19-072 §12.2)
- **Content-Length:** 88 bytes (issue body cites 86; the 2-byte
  difference comes from the `cfg.API.Title` / `cfg.API.Version` strings
  being slightly longer than the issue author's snapshot — substantively
  identical)
- **Body:** literally only `openapi` and `info` keys; `paths`,
  `components`, `servers`, `tags`, `security` all absent.

This response is **not a valid OpenAPI 3.0 document** because OAS 3.0.3
§4.7.1.1 marks `paths` as **REQUIRED** at the root OpenAPI Object.

## 2. Landing page advertises this URL as `service-desc`

```text
$ curl -s $base/ | jq '.links[] | select(.rel == "service-desc")'
{
  "href": "https://129-80-248-53.sslip.io/csapi-go-head/api",
  "rel":  "service-desc",
  "type": "application/vnd.oai.openapi+json;version=3.0",
  "title":"API definition"
}
```

- The link's `type` matches the response's `Content-Type` exactly.
- No alternative `service-desc` link with a different media type is
  offered, so content negotiation cannot route around the broken body.

## 3. `/conformance` declares `landing-page` (and hence binds the API-definition requirement)

```text
$ curl -s $base/conformance | jq '.conformsTo'
[
  "http://www.opengis.net/spec/ogcapi-common-1/1.0/conf/core",
  "http://www.opengis.net/spec/ogcapi-common-1/1.0/conf/landing-page",
  "http://www.opengis.net/spec/ogcapi-common-1/1.0/conf/json",
  "http://www.opengis.net/spec/ogcapi-common-2/1.0/conf/collections",
  "http://www.opengis.net/spec/ogcapi-connectedsystems-1/1.0/conf/api-common",
  "http://www.opengis.net/spec/ogcapi-connectedsystems-2/1.0/conf/api-common",
  ... (24 classes total, 1767 bytes)
]
```

Critical lines:

- `…/ogcapi-common-1/1.0/conf/landing-page` — declares the conformance
  class whose `/req/landing-page/api-definition-success` (a `SHALL`)
  the stub fails.
- `…/ogcapi-connectedsystems-1/1.0/conf/api-common` and
  `…/ogcapi-connectedsystems-2/1.0/conf/api-common` — Connected Systems
  profiles that incorporate the OGC API – Common landing-page
  requirements transitively.
- `…/ogcapi-common-1/1.0/conf/oas30` is **not** declared — so the
  stricter `/req/oas30/*` requirements are not directly binding (see
  spec-authority-2026-04-30.md §3 for nuance).

## 4. Reproduction script

```pwsh
$base = 'https://129-80-248-53.sslip.io/csapi-go-head'

# 1. Show /api response body and headers
curl.exe -s -i "$base/api"

# 2. Show service-desc link from landing page
curl.exe -s "$base/" | ConvertFrom-Json |
  Select-Object -ExpandProperty links |
  Where-Object { $_.rel -eq 'service-desc' }

# 3. Validate against OAS 3.0 schema (any tooling that uses
#    spec.openapis.org/oas/3.0/schema/2024-10-25 or similar will
#    reject the response: "must have required property 'paths'").
```

## Summary

The empirical reproduction in the issue body is exactly correct. The
stub is served on HEAD; its `Content-Type` matches the landing-page
advertisement; the `paths` field required by OAS 3.0.3 §4.7.1.1 is
missing; and cs-go's `/conformance` document binds the server to OGC
API – Common Part 1 `/req/landing-page/api-definition-success`, which
the stub fails.
